LLM Adapter Design Architecture

Primary: Qwen/Qwen2.5-72B-Instruct via router.huggingface.co
Fallback: mistralai/Mistral-7B-Instruct-v0.3 via same router
Strategy: Retry with fallback model on HTTP error or JSON parse failure
Safety: Only SELECT queries reach AlaSQL — DML blocked at validation layer

Production pattern:
Browser → LLM Adapter → HF Router → Qwen-72B ↓ (on failure) HF Router → Mistral-7B SQL layer: validate → AlaSQL → results → LLM narration

AI Failure Cases Documented 2 fixed

Failure 1 — Hallucinated JOIN (v1 prompt)
LLM generated: JOIN deliveries ON deliveries.order_id = orders.order_id
Error: deliveries has no order_id column.
Fix: Explicit schema annotation: "deliveries has NO FK to orders — do NOT join them."

Failure 2 — String boolean mismatch
LLM generated: WHERE is_cancelled = 'true'
Error: AlaSQL expects boolean literal.
Fix: Prompt rule: "BOOLEAN: use true/false not 'true'/'false'"

Scale Architecture Production Notes

Current (demo): 254KB data embedded · client-side AlaSQL · direct HF API calls
At 1M+ records: LLM generates SQL only → DuckDB/BigQuery executes → results piped back
Cost: Qwen-72B via HF ≈ $0.0009/1K tokens · effectively free at demo scale
Security: API key in sessionStorage only, never persisted · all queries logged with intent
